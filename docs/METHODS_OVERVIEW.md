# วิธีการที่เรา implement และสถานะโปรเจกต์

เอกสารสำหรับทีมและอาจารย์ (อัปเดต 2026-10-09) รายละเอียดเต็มอยู่ใน [PLAN.md](../PLAN.md), [MODELS.md](MODELS.md), [EVALUATION.md](EVALUATION.md)

## 1. ภาพรวมใน 5 บรรทัด
1. งาน: **multi-task video** ทำนาย optical flow และ depth จากวิดีโอ (MPI Sintel) ที่ถูกแปลงเป็นภาพบน "ตาแมลงหวี่" 721 hexal (ตาข่ายหกเหลี่ยม)
2. คำถามหลัก: โครงข่ายที่ผูกกับ **connectome จริง** ของตาแมลงหวี่ (flyvis) ดีกว่า connectome ที่ถูกสลับสาย (null) หรือไม่
3. เทียบกับ baseline ที่เป็น deep learning มาตรฐานบนตาข่ายเดียวกัน คือ **ConvGRU** ขนาดเท่ากัน (M4) และขนาดใหญ่ (M5)
4. ทุกโมเดลใช้ input, decoder, loss, จำนวน iteration และ optimizer เหมือนกัน เพื่อให้เทียบกันได้อย่างเป็นธรรม
5. สมมติฐาน H1–H7 และ analysis ถูกลงทะเบียนก่อนรัน และประเมินบน test set **ครั้งเดียว**

## 2. วิธีการที่ implement

### 2.1 Connectome-constrained network (flyvis, M1)
- **คืออะไร:** โครงข่ายประสาทที่โครงสร้างการเชื่อมต่อ (ชนิดเซลล์ต่อชนิดเซลล์, เครื่องหมายกระตุ้น/ยับยั้ง, kernel เชิงพื้นที่) มาจาก connectome ของตาแมลงหวี่
- **ทำงานอย่างไร:** เซลล์แต่ละตัวบนตาข่าย 721 ตำแหน่งส่งข้อความให้เพื่อนบ้านตามสายจริง มีพารามิเตอร์ให้เรียนรู้เพียงน้อยนิด (~0.7 k ตัว ไม่รวม decoder) เช่น ความแรงของ synapse และ time constant แล้วรันเป็น dynamics ต่อเนื่องตามเวลา
- **ทำไมใส่:** เป็น "สมมติฐาน" ของงานนี้: โครงสร้างทางชีววิทยาเป็น inductive bias ที่ดีหรือไม่
- **อ้างอิง:** flyvis (Lappalainen et al., Nature 2024)

### 2.2 Null connectomes (M2, M3)
- **คืออะไร:** M2 = สลับสายแบบรักษา degree (degree-preserving rewiring) ยังคงเครื่องหมายและ kernel เชิงพื้นที่ไว้ แต่สลับว่าชนิดไหนต่อกับชนิดไหน; M3 = กราฟสุ่ม (Erdős–Rényi) จำนวนเส้นและสัดส่วนเครื่องหมายเท่าเดิม
- **ทำงานอย่างไร:** สุ่มเลือกคู่เส้นเชื่อมแล้วสลับปลายกัน ทำซ้ำหลายครั้ง จำนวนเส้นเข้า/ออกของแต่ละ node จึงไม่เปลี่ยน แต่ "ใครต่อกับใคร" ถูกทำลาย
- **ทำไมใส่:** ถ้า M1 ดีกว่า M2 แปลว่าประโยชน์มาจาก wiring เฉพาะ ไม่ใช่แค่สถิติระดับกราฟหรือขนาดโมเดล (M3 เป็น null ที่อ่อนกว่า)
- **อ้างอิง:** Maslov & Sneppen, Science 2002

### 2.3 HexConvGRU บนตาข่ายหกเหลี่ยม (M4, M5)
- **คืออะไร:** ConvGRU ที่ convolution ทำงานบนตาข่าย hex โดยตรง (เพื่อนบ้าน 6 ทิศ) ไม่ต้องแปลงเป็นภาพสี่เหลี่ยม M4 ขนาดเท่า M1, M5 ใหญ่ (~0.5–1 M พารามิเตอร์)
- **ทำงานอย่างไร:** ทุกเฟรมมี hidden state ต่อ hexal; gate ตัดสินใจว่าจะจำอะไรไว้และอัปเดตอะไรจากเฟรมใหม่ ทำให้ประมาณการเคลื่อนที่ข้ามเฟรมได้
- **ทำไมใส่:** baseline มาตรฐานที่ต้องชนะ ถ้า connectome แพ้ M4 ที่ขนาดเท่ากัน ข้ออ้างเรื่อง prior ชีวภาพก็ไม่มีน้ำหนัก
- **อ้างอิง:** baseline มาตรฐานของงาน video (ConvGRU); ดู MODELS.md

### 2.4 Hybrid front-end (M6, M7)
- **คืออะไร:** ใช้ front-end (M1 สำหรับ M6; M2 สำหรับ M7) ต่อกับ trunk แบบ HexConvGRU แล้ว decode
- **ทำงานอย่างไร:** front-end แปลงภาพเป็น feature ชีวภาพก่อน แล้ว GRU ทำ temporal reasoning ต่อ ฝึกร่วมกันทั้งชุด
- **ทำไมใส่:** ทดสอบว่า connectome มีประโยชน์ในฐานะ "ตัวสกัด feature" หรือไม่ (H4 M6 vs M4, H5 M6 vs M7 เพื่อแยกว่าประโยชน์มาจาก wiring จริง)
- **อ้างอิง:** PLAN.md amendment A5

### 2.5 Frozen front-end + zero-init residual (M6f, M7f)
- **คืออะไร:** front-end คือ checkpoint M1 (หรือ M2) ของ seed เดียวกันที่ **แช่แข็ง** เอาต์พุต = เอาต์พุตของ front-end + ส่วนเสริม (residual) จาก HexConvGRU
- **ทำงานอย่างไร:** layer สุดท้ายของ residual เริ่มที่ศูนย์ การฝึกจึงเริ่มจากคำตอบของ M1/M2 พอดี แล้วเรียนรู้เฉพาะ "ส่วนที่ขาด"
- **ทำไมใส่:** วัดว่าความรู้ใน connectome ที่เรียนไว้แล้วเสริมด้วย GRU ได้ดีกว่า wiring สุ่มหรือไม่ (H7) โดยไม่ให้ trunk กลบ front-end
- **อ้างอิง:** Zhang, Rao & Agrawala, ControlNet (zero convolutions), ICCV 2023; Johannink et al., Residual Reinforcement Learning for Robot Control, ICRA 2019

### 2.6 Recurrent depth: HexConvGRU-K (M8)
- **คืออะไร:** สถาปัตยกรรม/พารามิเตอร์เท่า M4 แต่วน GRU cell เดิม K รอบต่อเฟรม (น้ำหนักร่วมกัน) พร้อมป้อน input เดิมซ้ำทุกรอบ
- **ทำงานอย่างไร:** ฝึกโดยสุ่ม K จาก {1..4} ตอนใช้งานเลือก K ได้ตามงบเวลา (any-time): K มาก = คิดนานขึ้น แม่นขึ้น โดยไม่เพิ่มพารามิเตอร์
- **ทำไมใส่:** "ความลึกเพิ่ม" ฟรีในแง่พารามิเตอร์ และได้กราฟ K เทียบ EPE ที่ตรวจสอบง่าย (H6: M8 K=4 ชนะ M4)
- **อ้างอิง:** Dehghani et al., Universal Transformers, ICLR 2019; Geiping et al., arXiv:2502.05171, 2025

### 2.7 Floors (เส้นพื้น) รวม Lucas–Kanade บน hex lattice
- **คืออะไร:** ตัวเทียบที่ไม่ใช่โมเดลเรียนรู้: zero-flow, train-mean flow, **Lucas–Kanade** (classical) บนตาข่าย hex, และสำหรับ depth: train-mean / per-hexal train-mean
- **ทำงานอย่างไร:** LK แก้ระบบสมการเชิงเส้นจาก gradient ของความสว่างในหน้าต่างเล็ก ๆ เพื่อหา flow เราปรับแบบ **4 พารามิเตอร์ (calibration)** โดย fit บน train เท่านั้น และมี **oracle** (ใช้ flow จริงของเฟรมก่อนหน้า) ไว้เป็นเพดานอ้างอิง ไม่ใช่คู่แข่ง
- **ทำไมใส่:** ทุกผลรายงานเป็น "margin เหนือ floor ที่ดีที่สุด" เพื่อไม่ให้ตัวเลข EPE ที่ดูดีหลอกเรา
- **อ้างอิง:** Lucas & Kanade, IJCAI 1981

### 2.8 Claim ladder, pre-registration, test-once
- **คืออะไร:** ทุกข้อสรุปติดป้าย **L1** = ลงทะเบียนล่วงหน้า + วัดบน test, **L2** = ลงทะเบียนแต่ใช้ val เท่านั้นหรือบางส่วน, **L3** = เชิงสำรวจ
- **ทำงานอย่างไร:** PLAN.md และ amendment A1–A8 เขียนก่อนรัน (amendment หลัง probe ถูกเปิดเผยว่าเป็น post-probe); hyper-parameter เลือกจาก val; test ประเมินครั้งเดียวด้วยสคริปต์ที่ตรวจบน val แล้ว
- **ทำไมใส่:** กันการ "เลือกผลที่ชอบ" และทำให้รู้ว่าข้ออ้างแต่ละข้อมีน้ำหนักเท่าไร
- **อ้างอิง:** Nosek et al., The preregistration revolution, PNAS 2018

### 2.9 Speed engineering
- **Fused Triton kernel สำหรับ sparse message passing:** เดิมหนึ่ง ODE step ต้องวนผ่านเส้นเชื่อมประมาณ 6 รอบ (gather, คูณ, scatter, ฯลฯ แต่ละรอบอ่าน/เขียนหน่วยความจำ GPU) "fusion" คือรวมขั้นตอนเหล่านี้เป็น kernel เดียวที่ผ่านเส้นเชื่อมรอบเดียว โดยเขียน backward เอง งานนี้ memory-bound จึงลด traffic = เร็วขึ้น ผลคือเร็วขึ้น **2.4×** (0.0738 s/iter) และใช้ VRAM 0.48 GB ตรวจ **parity** กับ implementation เดิมแล้ว (ผ่านเกณฑ์ ≥ 2× + parity; ดู [R2_BENCHMARK.md](R2_BENCHMARK.md))
- **torch.compile:** เร็วขึ้นประมาณ **5×** กับ M4 (ลดภาระ Python/launch) ไม่ bit-identical แต่ loss ใกล้เคียง (บันทึกใน A8)
- **Fused penalty:** รวมการคำนวณ activity penalty ของ flyvis เป็นเส้นทางเดียว (เร็วขึ้นประมาณ 1.13×, ทดสอบความเท่ากันแล้ว)
- **ทำไมใส่:** ทำให้ grid 39 รอบ x 30k iteration รันได้บน GPU 8 GB ในเวลาไม่กี่วัน

## 4. แนวโน้มเบื้องต้น (VAL ONLY, L2)
**ข้อควรระวัง: ตัวเลขด้านล่างเป็น validation เท่านั้น เลือก best checkpoint จาก val loss ตัวเลข 3 seed ยังมี noise สูง ไม่ใช่ผลลัพธ์ของโครงการ และไม่ใช่การทดสอบสมมติฐาน**

|---|---|
| floor: Lucas–Kanade | 4.71 |
| floor: zero-flow | 5.07 |
| M4 (ConvGRU เล็ก) | 4.61 / 4.59 / 4.60 |
| M8 (recurrent depth) | 4.52 / 4.51 / 4.52 |
| M5 (ConvGRU ใหญ่, seed 0 เท่านั้น) | 4.49 |
| M1 (connectome) | 4.97 / 4.91 / 4.64 |
| M2 (rewired) | 4.88 / 4.85 / 4.95 |
| M3 (random) | 4.78 / 4.85 / 4.82 |
| M6 | 4.80 / 4.78 / 4.69 |
| M7 | 4.81 / 4.66 / 4.46 |
| M6f | 4.81 / 4.68 / 4.65 |
| M7f | 4.60 / 4.75 / 4.75 |
| M1 ที่ข้อมูล 25% | 5.00 / 5.02 / 4.99 |
| M2 ที่ข้อมูล 25% | 5.01 / 4.93 / 5.07 |

Depth RMSE ที่น่าสังเกต: M6 seed 0 ดีที่สุด (1.27); M4 = 1.60 / 1.47 / 1.33

**อ่านอย่างไร (ภาษาง่าย ๆ):**
- **Recurrent depth (M8) ช่วยได้โดยไม่เพิ่มพารามิเตอร์:** M8 ต่ำกว่า M4 ทุก seed (ประมาณ 0.08–0.09) และแทบนิ่งข้าม seed
- **wiring ของ connectome ยังไม่ดีกว่า rewired/random:** M1 ไม่ต่ำกว่า M2/M3 อย่างสม่ำเสมอ (seed 2 ของ M1 ดี แต่ seed 0/1 ไม่)
- **โมเดล connectome ส่วนใหญ่ยังอยู่ต่ำกว่า floor ของ LK (4.71):** หมายถึง EPE สูงกว่า LK ในหลายรอบ คือยังไม่ชนะวิธีคลาสสิกที่ไม่ต้องเรียนรู้
- **ข้อมูล 25% น้อยเกินไปสำหรับ flow:** M1/M2 ที่ 25% อยู่ราว 5.0 ใกล้ zero-flow (5.07) จึงบอกอะไรเรื่อง data efficiency ได้จำกัด

## 5. ผลลัพธ์ที่คาดหวังเมื่อได้ test
ทั้งหมดเป็นการคาดเดาจาก val และอาจผิด ผลจริงบน test คือสิ่งที่ตัดสิน

| สมมติฐาน | ทิศทางที่น่าจะเป็น (hedged) | ความหมายของแต่ละผล |
|---|---|---|
| H1 M1 < M2 (3/3 seed, ทั้งสอง task) | น่าจะไม่ผ่าน: M1 กับ M2 ซ้อนทับกันมากบน val | ผ่าน = wiring จริงมีข้อมูลเฉพาะ; ไม่ผ่าน = ประโยชน์ (ถ้ามี) มาจากสถิติกราฟ/ขนาด ไม่ใช่ wiring |
| H2 M1 ชนะ M4 ทั้งสอง task | น่าจะไม่ผ่านบน flow (M4 ต่ำกว่า M1 บน val) | ไม่ผ่าน = prior ชีวภาพไม่ชนะ DL เล็กที่ parameter เท่ากันในงานนี้ ซึ่งเป็นผลลบที่รายงานได้ตรงไปตรงมา |
| H3 ช่องว่างที่ 25% ใหญ่กว่าที่ 100% | ไม่แน่ใจ; 25% ใกล้ floor จึงอาจวัดไม่ได้ | เชิงพรรณนา รายงานไม่ว่าผลจะเป็นอย่างไร |
| H4 M6 ชนะ M4 (flow และ depth) | ไม่แน่: depth อาจดี (M6 seed 0 = 1.27) แต่ flow ไม่ชัด | ผ่าน = connectome front-end เสริม GRU ได้; ไม่ผ่าน = GRU อย่างเดียวพอ |
| H5 M6 ชนะ M7 (3/3 seed) | น่าจะไม่ผ่าน: M7 บางรอบดีกว่า | ถ้า H4 ผ่านแต่ H5 ไม่ผ่าน = ประโยชน์มาจากโครงสร้าง hybrid ไม่ใช่ connectome เฉพาะ |
| H6 M8 (K=4) ชนะ M4 (≥ 2/3 seed) | **น่าจะผ่านที่สุด** val ชี้ทิศทางสม่ำเสมอ | ผ่าน = recurrent depth ช่วยจริงและ any-time ใช้ได้ |
| H7 M6f ชนะ M7f (3/3 seed) | น่าจะไม่ผ่าน: ผลสลับกันตาม seed | ไม่ผ่าน = frozen connectome ไม่ให้ข้อได้เปรียบเหนือ rewired |

ผลรวมที่เป็นไปได้: ถ้า connectome ไม่ชนะ null และไม่ชนะ floor เราจะรายงานเป็น **ผลลบที่ลงทะเบียนไว้** (ไม่ใช่ความล้มเหลวของโครงการ) พร้อมคำอธิบายที่ทดสอบเพิ่มได้ (L3)

## 6. สิ่งที่ได้จากโปรเจกต์ (ไม่ว่าผลจะออกมาอย่างไร)
- **การเปรียบเทียบที่เป็นธรรมและลงทะเบียนล่วงหน้า** ระหว่าง prior ชีวภาพกับ null และ DL มาตรฐาน (input, loss, iteration, optimizer เหมือนกัน; 3 seed)
- **Floors ที่ทำให้ข้ออ้างซื่อตรง:** LK, zero-flow, oracle บอกว่าโมเดลเหนือ "ของง่าย ๆ" จริงหรือไม่
- **เทคนิค any-time recurrent depth ราคาถูก:** เพิ่มคุณภาพได้โดยไม่เพิ่มพารามิเตอร์ (ถ้า H6 ผ่าน)
- **GPU kernel ที่มีประสิทธิภาพ:** ทำให้เทรน flyvis ได้บน GPU ระดับ laptop 8 GB (เร็ว 2.4×, parity ตรวจแล้ว)
- **ข้อจำกัดที่เปิดเผย:** ไม่ได้ปรับ lr แยกต่อโมเดล (งบเวลา); flow อยู่บน Sintel (ซึ่งเป็นภาพสังเคราะห์) เท่านั้น; 3 seed ต่อรุ่น; amendment หลัง probe (post-probe แต่ก่อน grid); ข้อมูล 25% อ่อนเกินไป; compile ไม่ bit-identical
