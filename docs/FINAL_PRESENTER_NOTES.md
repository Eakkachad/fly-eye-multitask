## 1. ต่อสไลด์

### สไลด์ 1: cover (#8)
**พูดอะไร:** สวัสดีครับ/ค่ะ กลุ่มเรามี 8 คน นำเสนอผลโปรเจกต์ Deep Learning for Image Analysis เรื่องทำนาย optic flow และ depth จากวิดีโอผ่านตาแมลงหวี่. คราวที่แล้วเราเสนอสมมติฐาน วันนี้เป็นผลจริงบน test ที่แยกไว้ ซึ่งผลส่วนใหญ่ออกมาตรงข้ามกับที่หวัง และเราจะเล่าอย่างตรงไปตรงมาว่าได้เรียนรู้อะไร
**ตัวเลขที่ต้องจำ:** 54 runs, test ใช้ครั้งเดียว 2 ชุด.
**ระวัง:** อย่าเปิดด้วยคำว่า "สำเร็จ"; เปิดด้วยว่าเป็นผลที่ลงทะเบียนไว้ล่วงหน้า.

### สไลด์ 2: คำถามและงาน (#8)
**พูดอะไร:** คำถามเดียว: wiring จริงของสมองแมลงหวี่ ช่วยให้ deep learning ทำนายได้ดีขึ้นกว่า wiring สลับสายหรือ ConvGRU ขนาดเท่ากันไหม. งานคือ multi-task: flow และ depth ในแบบจำลองเดียว รายงานแยกงาน และใช้ข้อมูลข้ามเฟรม (video). Phase 2 เราเพิ่มวิธีของเราเองและทดสอบบนข้อมูลต่างโดเมนอีกชุด.
**ตัวเลขที่ต้องจำ:** 721 hexal, 19 เฟรม/clip; 2 งาน (flow, depth).
**ระวัง:** "multi-task" ต้องชี้ได้ว่ามี 2 head ในโมเดลเดียว และรายงานแยก (เกณฑ์ 4 คะแนน).

### สไลด์ 3: ข้อมูล (#1)
**พูดอะไร:** ใช้ Sintel 23 ฉากที่มี GT ทั้ง flow และ depth แล้ว render ลงตาข่ายหกเหลี่ยมของตาแมลงด้วย flyvis. เราแบ่งตามตระกูลฉาก ไม่ใช่รายเฟรม เพราะเฟรมติดกันแทบเหมือนกัน ถ้าสุ่มรายเฟรม test จะง่ายเกินจริง. Test Sintel คือ bandage/cave 4 ฉาก 200 เฟรม. ชุดที่สองคือ Spring ซึ่งต่างโดเมน เราเลือก 8 sequence ด้วย seed ก่อนดูเนื้อหา.
**ตัวเลขที่ต้องจำ:** train 15 ฉาก/674 เฟรม; val 4 ฉาก/190; test 4 ฉาก/200; Spring 8 sequence = 24 clip; seed แบ่ง 20261005, เลือก Spring 20261010.
**ระวัง:** Spring GT ช้ามาก (zero-flow EPE = 0.4997 = ความเร็วเฉลี่ย GT) ต้องบอกเมื่อพูดถึงตัวเลข EPE. Sintel test มีแค่ 2 ตระกูลฉาก: sequence จากฉากเดียวกันไม่อิสระ.

### สไลด์ 4: โมเดลที่เปรียบเทียบ (#2, #3, #4)
**พูดอะไร:** [#2] M1 คือ connectome จริงของ flyvis เรียนจากศูนย์ ~15k พารามิเตอร์รวม decoder. [#3] M2 คือสลับสายแบบรักษา degree, M3 คือกราฟสุ่ม: ถ้าความรู้อยู่ใน "ใครต่อกับใคร" M1 ต้องชนะสองตัวนี้. [#4] M4 = HexConvGRU ขนาดเท่า M1, M5 = ใหญ่ 604k, M8 = วน GRU K รอบ (weight-tied). ยังมี hybrid M6/M7 (front-end จริง/สลับ + GRU) และ M6f/M7f (แช่แข็ง front-end + residual). ทั้งหมดเทรนข้อมูล/iteration/loss เท่ากัน.
**ตัวเลขที่ต้องจำ:** M1/M2/M3 = 15,387; M4 = 15,402 (match รวม decoder, A1); M5 = 604,835; Ours-S 15,402; Ours-L 274,323.
**ระวัง:** M5 ไม่ใช่ param-matched (ใช้เป็นเพดานของ deep learning). Ours-L ก็ไม่เท่ากับ M5.

### สไลด์ 5: วิธีของเรา (#8)
**พูดอะไร:** วิธีของเราคือ M8 บวกสามอย่าง: EPE loss (ตรงกับตัวชี้วัด), scale-invariant depth loss (Eigen et al. 2014) กันปัญหา scale ของ depth ต่างกันข้ามฉาก, และ init-normalised task weights ปรับน้ำหนัก 2 งานให้เริ่มสมดุล. recurrent depth คือวน GRU ซ้ำหลายรอบด้วยน้ำหนักเดียวกัน ให้ "คิดนานขึ้น" โดยไม่เพิ่มพารามิเตอร์. มี 2 ขนาด: Ours-S (เท่า M4) และ Ours-L (274k).
**ตัวเลขที่ต้องจำ:** ablation 3 อัน: noEPE, K1, noSI.
**ระวัง:** อย่าบอกว่า "เราคิดค้น" recurrent depth/SI loss: เป็นการประกอบวิธีที่มีในงานวิจัย (Dehghani 2019, Geiping 2025, Eigen 2014) แล้วทดสอบอย่างแฟร์.

### สไลด์ 6: protocol (#5)
**พูดอะไร:** ก่อนรันเราเขียน pre-registration A1-A9 ซึ่งกำหนดสมมติฐาน เกณฑ์ผ่าน/ไม่ผ่าน และ floors. Floors คือ zero-flow, Lucas-Kanade, train-mean/constant depth รายงานคู่โมเดลทุกครั้ง. Test ใช้ครั้งเดียว 2 ชุด: Sintel test (phase 1) และ Spring (phase 2); Sintel test ถูกใช้หมดแล้ว ส่วนที่รันซ้ำเป็น "ดูซ้ำ" L2. 3 seed ต่อ arm, เทรน 30k iter เท่ากัน. Phase 2 รายงาน checkpoint สุดท้ายเป็นหลัก เพราะ val ไม่ทำนาย test.
**ตัวเลขที่ต้องจำ:** A1-A9; 3 seed; 30k iter; กฎ last-vs-best ตัดสินก่อนเห็นผล Spring (A9).
**ระวัง:** phase 1 ใช้ best.pt (เลือกบน val) ส่วน phase 2 ใช้ last -> สองชุดตัวเลขเทียบตรง ๆ ไม่ได้ ต้องบอกเอง.

### สไลด์ 7: ผล Sintel test (#6)
**พูดอะไร:** บน Sintel test มีโมเดลเดียวที่ชนะ LK คือ M5 (5.253 vs 5.337). M4 5.411 ดีกว่า M1 5.590 ซึ่งใกล้เคียง M2 5.605 และ M3 5.627. M1, M2, M3 ต่างกันไม่เกินหนึ่ง sd. ภาพรวม: งานยาก และ wiring จริงไม่ให้ประโยชน์เหนือ null (L1). ผลแบบนี้คือคำตอบของคำถามหลักของเรา ไม่ใช่ความล้มเหลวของการทดลอง.
**ตัวเลขที่ต้องจำ:** M5 5.253 +- 0.185 (sd ใหญ่ เพราะ gain จาก cave_2 เป็นหลัก); M4 5.411 +- 0.022; M1 5.590 +- 0.036; zero 5.620; LK 5.337.
**ระวัง:** ห้ามพูดว่า "M5 ชนะอย่างมั่นใจ" (sd 0.185, 3 seed, gain 65% มาจาก cave_2). ห้ามพูดว่า "connectome แย่": พูดว่า "ไม่ดีกว่า null/M4 ที่ขนาดเท่ากัน".

### สไลด์ 8: depth (#6)
**พูดอะไร:** ด้าน depth บน Sintel test ไม่มี run ไหนชนะ floor: 0 จาก 39 run (RMSE 0.817-1.356 vs floor 0.766). ที่น่าสนใจคือบน val ทุกโมเดลชนะ floor (30/30) จึงเป็นตัวอย่างที่ val ให้ข้อสรุปผิด. สาเหตุที่เห็นคือ test อยู่ใกล้ค่าเฉลี่ยของ train พอดี floor จึงต่ำ ไม่ใช่ floor ฉลาด (L3). Spring วัด depth หลังจัด alignment ด้วย median ต่อ clip.
**ตัวเลขที่ต้องจำ:** floor 0.766; 0/39 test, 30/30 val; log-depth sd train 1.816, test 1.359; hybrid M6/M7 ดีสุดที่ ~0.857-0.859 (ยังแพ้ floor).
**ระวัง:** "โมเดลเรียนรู้ depth ไม่ได้" เป็นข้อสรุปที่เกินหลักฐาน; พูดว่า "ไม่ชนะ floor ง่าย ๆ ที่ใกล้ distribution ของ test".

### สไลด์ 9: ผล Spring (#6)
**พูดอะไร:** บน Spring ไม่มีโมเดลชนะ zero-flow หรือ LK ด้าน flow. ในกลุ่มที่เรียนรู้ null M2/M3 ดีที่สุด (0.555/0.574) แล้ว Ours-S 0.590 ซึ่งชนะ M4 (0.649) ครบ 3/3 seed. Ours-L (0.809) แย่กว่า Ours-S: ใหญ่ขึ้นไม่ได้ดีขึ้น. M1 เฉลี่ยอ่านไม่ได้เพราะ seed 1 ระเบิด (กราฟใช้แกนขาด).
**ตัวเลขที่ต้องจำ:** M2 0.555 +- 0.042; Ours-S 0.590 +- 0.015; M4 0.649; LK 0.4655; zero 0.4997. Depth aligned: M2 0.901, Ours-S 0.939, floor 0.9362.
**ระวัง:** Ours-S ไม่ชนะ M2/M3 (ต่างกันเล็ก 0.035 และ sd ของ M2/M3 0.04-0.07) และไม่ชนะ floors. "ดีที่สุดในกลุ่ม deep learning ขนาดเท่ากัน" ถูกต้อง; "ดีที่สุด" เฉย ๆ ผิด. Depth ของ Ours-S ไม่ชนะ floor (-0.3%).

### สไลด์ 10: hypothesis board (#3)
**พูดอะไร:** จากสมมติฐานที่ลงทะเบียนไว้ ไม่มีข้อไหนผ่านเต็ม. H1 (M1 ชนะ M2) ไม่ผ่าน ชนะ 1/3 seed ทั้ง EPE และ depth. H2 (M1 ชนะ M4) ไม่ผ่าน. H4-H7 (hybrid, recurrent, frozen) ไม่ผ่าน. H3 ผ่านบางส่วน 2/4 การเปรียบเทียบ. P1-P3 ของ phase 2 ไม่ผ่านตามเกณฑ์ P4 เป็นการบรรยาย. ข้อสรุปที่แข็งแรงคือ "ไม่ผ่าน" เพราะเกณฑ์กำหนดก่อนเห็นผล.
**ตัวเลขที่ต้องจำ:** H1 1/3 + 1/3; H4 EPE 0/3 แต่ RMSE 3/3 (0.857 vs 0.976); H5 0/3; H6 0/3; H7 1/3; P2 EPE 3/3 แต่ depth 1/3; P3 noEPE 2/3, K1 2/3, noSI 1/3.
**ระวัง:** H4 มีส่วนที่ดี (depth ชนะ 3/3) แต่เกณฑ์ต้องชนะทั้งสองงาน -> ไม่ผ่าน; ห้ามเลือกเล่นเฉพาะส่วนที่ดี. ทุกข้อเป็น L1.

### สไลด์ 11: ablation (#8)
**พูดอะไร:** ถอดทีละส่วนของวิธีเรา บน Spring: ถอด EPE loss แย่ลง 2/3 seed (+0.052), K1 แย่ลง 2/3 (+0.024), ถอด SI loss แย่ลงแค่ 1/3 ตามเกณฑ์ (ผ่านเกณฑ์ลงทะเบียน = ไม่ผ่านสำหรับ SI). สรุป: EPE loss และการวนหลายรอบช่วยเล็กน้อย, scale-invariant depth loss ไม่ช่วย. ขนาดผลเล็ก (mean dEPE 0.024-0.068).
**ตัวเลขที่ต้องจำ:** noEPE 2/3, K1 2/3, noSI 1/3 (depth), ต่อ sequence noEPE/noSI แย่กว่า 8/8 sequence (ค่าเฉลี่ย seed, L3).
**ระวัง:** 2/3 seed จาก 3 = หลักฐานอ่อน; พูด "ช่วยเล็กน้อย สอดคล้องกัน" ไม่ใช่ "พิสูจน์แล้ว".

### สไลด์ 12: recurrent depth any-time (#4)
**พูดอะไร:** any-time คือโมเดลเดียวที่เลือกจำนวนรอบ K ตอน inference ได้. บน Sintel test M8 ดีขึ้นทุก seed เมื่อเพิ่ม K: 5.769 -> 5.621 -> 5.586 -> 5.578 แต่ผลตอบแทนลดเร็ว (K3 -> K4 ลด 0.009 ซึ่งเล็กกว่า sd ข้าม seed 0.094) และทุก K ยังแย่กว่า M4. บน Spring ไม่เป็นแบบนั้น: Ours-S 0.580 -> 0.590 (flat), M8 แย่ลงตาม K (0.893 -> 1.670).
**ตัวเลขที่ต้องจำ:** Sintel K1 5.769 / K4 5.578; Spring Ours-S K1 0.580 / K4 0.590 (K4 ไม่ดีกว่า K1 ใน 0/3 seed); Ours-L 0.908 -> 0.809 (3/3 seed).
**ระวัง:** "K มากขึ้นดีขึ้นเสมอ" ถูกเฉพาะ "ภายในโมเดลเดียวบน Sintel" ห้ามพูดข้ามโดเมน. K1 ที่เทรน K=1 แล้ว eval K สูงแย่ลง (0.623 -> 0.744) = extrapolation ไม่ได้.

### สไลด์ 13: ตัวอย่างดี/แย่ (#7)
**พูดอะไร:** ภาพเลือกตัวอย่างดีและแย่เพื่อให้เห็นลักษณะความผิดพลาด ไม่ใช่เพื่อพิสูจน์ผล (เลือก post hoc, L3). ที่ดี: บริเวณเคลื่อนที่ช้า/เรียบ. ที่แย่: ขอบวัตถุที่เร็ว, บริเวณ GT เร็ว (>16 หน่วยคือ 10% ของพิกเซลแต่ 44% ของ error) ซึ่งโมเดลแทบไม่ได้อะไรเหนือ zero-flow.
**ตัวเลขที่ต้องจำ:** ความเร็ว >16 = 10% pixel / 44% error; ที่ GT ช้า (<1 หน่วย) โมเดลแย่กว่า zero-flow.
**ระวัง:** ต้องบอกว่าตัวอย่างเลือกหลังเห็นผล (seed 0) ไม่ใช่ตัวแทน.

### สไลด์ 14: ทำไม depth/test ต่างกัน (#7)
**พูดอะไร:** val ไม่สะท้อน test. Val เป็น market/mountain ที่ log-depth เฉลี่ย 3.47 ส่วน test (bandage/cave) 0.87 ใกล้ train (1.14). ดังนั้น floor ของ test ต่ำมาก (0.766) แต่ floor ของ val สูง (1.863) ทำให้ทุกโมเดล "ชนะ" บน val. ภายในโมเดลเดียว ความสัมพันธ์ val-test มีแค่ r = 0.09; ชนะ LK บน val 16/30 แต่บน test 2/30. 66% ของ MSE ของ depth เป็น bias^2 และ correlation ภายใน sequence ติดลบ (-0.31) บน test.
**ตัวเลขที่ต้องจำ:** r = 0.09; 16/30 vs 2/30; margin เหนือ zero-flow 0.377 -> 0.113; bias^2 66%; sd ของทำนาย 0.15 vs GT 0.36.
**ระวัง:** ทั้งหมด L3. อย่าอ้างว่ารู้สาเหตุเดียว: พูดว่า "การกระจาย depth ต่าง split คือสิ่งที่เห็นชัด". ชนะ floor เฉพาะ bandage แพ้ cave ทุก run.

### สไลด์ 15: ทำไมทายการเคลื่อนไหวเกิน (#7)
**พูดอะไร:** บน Spring GT ช้า โมเดลที่เทรนบน Sintel (เร็วกว่า) ทายความเร็วเกินในบริเวณนิ่ง. ประมาณอัตราส่วน |ทำนาย|/|GT| (ประมาณจาก EPE และมุม): M2/M3 ~0.44-0.45, Ours-S ต่ำกว่าเดิม, M4 ~1.06, M8 ~3.22, Ours-L ~1.59. ใน sequence เกือบนิ่ง (0007) M2 ทายเกิน 4.1x แต่ M1/M4 ทายเกิน 8.0x/7.4x. เห็นว่า null "หด" เอาต์พุตเข้าหาศูนย์ ซึ่งได้เปรียบเมื่อ GT ช้า.
**ตัวเลขที่ต้องจำ:** zero-flow = ความเร็ว GT เฉลี่ย 0.4997; sequence 0033 = 7% ของ hexal แต่ 47% ของ zero-flow EPE; ไม่มี arm ชนะ zero เกิน 1/8 sequence.
**ระวัง:** ความเร็วทำนายเป็นค่า **ประมาณ** (per_pixel ไม่เก็บค่าทำนาย; ทดสอบกับข้อมูลสังเคราะห์ อัตราส่วน 1.02). คำอธิบายว่า "การ regularise ของ wiring ที่สลับ" เป็นสมมติฐาน (H-a) ยังไม่ทดสอบ ห้ามพูดเป็นข้อเท็จจริง.

### สไลด์ 16: M1 ระเบิด (#2, #7 ช่วย)
**พูดอะไร:** M1 seed 1 บน Spring ได้ EPE 254.5 ขณะ seed 0 และ 2 ได้ 0.527 และ 0.718. ระเบิดเฉพาะ sequence 0001 (3 clip ยาว 515 ก้าว), เริ่มโตหลังก้าว ~300 แล้วโตแบบ exponential ~6.5x ต่อ 10% ของ clip, อีก 21 clip ปกติ. best.pt (iter 20000) ได้ 0.718 แต่ last (iter 30000) ได้ 254.5 คือเกิดตอนท้ายการฝึก. เรายืนยันแล้วว่าซ้ำได้โดยไม่ใช้ fused kernel (ไม่ใช่บั๊ก kernel). ลักษณะคือ dynamics แบบ ODE/recurrent ไม่เสถียร.
**ตัวเลขที่ต้องจำ:** 254.46; seed อื่น 0.527/0.718; clip ยาวสุดที่ไม่ระเบิดมี 307 ก้าว; sequence 0001 EPE 997; 7.2% ของ hexal-frame มี EPE > 5 (seed อื่น ~2%).
**ระวัง:** 1 ใน 3 seed ไม่ใช่ข้อสรุปว่า "สมองแมลงไม่ดี": พูดว่า "การ train M1 ที่ 30k iter ไม่เสถียรข้ามโดเมนเมื่อ rollout ยาว". สาเหตุราก (H-b) ยังไม่ทดสอบ. ไม่ตัด seed ทิ้ง: รายงานทั้งค่าเฉลี่ย (85.24 +- 146.56) และแยก seed.

## 2. กลยุทธ์เล่าผลลบ (ให้เป็นจุดแข็ง พร้อมหลักฐาน)
1. **เล่าเป็น "คำตอบ" ไม่ใช่ "ความล้มเหลว":** คำถามของเราคือ "wiring จริงช่วยไหม" คำตอบที่ตรวจสอบได้คือ "ไม่ช่วยเหนือ null ที่ขนาดและเงื่อนไขเท่ากัน (L1)". หลักฐาน: H1 ชนะ 1/3 seed, M1 5.590 vs M2 5.605 บน Sintel.
2. **ชี้ว่าเกณฑ์กำหนดก่อน:** pre-registration A1-A9 ทำให้ผลลบน่าเชื่อ: เราเปลี่ยนเกณฑ์หลังเห็นผลไม่ได้. พูดประโยค "เรากำหนดว่าอะไรคือผ่านก่อนรัน".
3. **ผลลบมาพร้อมกลไกที่ตรวจได้:** ไม่ใช่แค่ "ไม่ชนะ" แต่บอกว่าเห็นอะไร (L3): depth test ใกล้ train mean, ทายความเร็วเกินบน Spring, M1 ไม่เสถียรที่ rollout ยาว.
4. **ใช้ floors เป็นเครื่องวัดความจริง:** โมเดลที่ "ดูดี" บน val (ชนะ floor 30/30) ไม่ชนะบน test (0/39). ถ้าไม่มี floor เราจะรายงานผิด -> นี่คือคุณค่าของวิธีวิจัย.
5. **val ไม่ใช่ test:** r = 0.09, margin หด 0.377 -> 0.113: เราจับได้เพราะเก็บ test ไว้ใช้ครั้งเดียว และเปลี่ยนกฎเลือก checkpoint (A9) ก่อนเห็นผล Spring.
6. **มีผลบวกที่ซื่อสัตย์ แต่ติดป้ายระดับ:** Ours-S ชนะ M4 3/3 seed บน Spring flow (L1), EPE loss และ recurrence ช่วย 2/3 seed; พร้อมกันนั้นบอกว่าไม่ชนะ floors และ depth ไม่ผ่าน.
7. **ผลลบข้ามโดเมน (null ดีสุด) = สัญญาณว่า prior ของ wiring จริงไม่ได้ทำให้ทั่วไปขึ้น** ไม่ใช่ตัวเลขที่เลือกมา: รายงานทั้ง M1 ระเบิด ไม่ตัดทิ้ง.
8. **อย่าทำ:** ห้ามเปลี่ยนเรื่องเป็น "แต่ speed ดีขึ้น"; ห้ามอ้างข้อเดียวที่ผ่านเป็นภาพรวม; ห้ามเปลี่ยนเกณฑ์; ห้ามหลบคำว่า "ไม่ผ่าน".
**ประโยคสำเร็จรูป:** "ผลนี้ไม่ได้ตรงกับที่หวัง แต่ตรงกับที่เราลงทะเบียนไว้ล่วงหน้าว่าจะรายงาน และเรามี floor กับ null ที่ทำให้บอกได้ว่าไม่ใช่เพราะเทรนพลาด"

## 3. Glossary เพิ่มเติม
- **scale-invariant loss (depth):** loss ที่ไม่ลงโทษการคูณ/ขยับ scale ทั้งภาพ (Eigen 2014) ให้ความสำคัญกับโครงสร้างสัมพัทธ์ของ depth. ในงานเรา ไม่ช่วย (noSI แย่กว่าเพียง 1/3 seed).
- **recurrent depth / any-time:** วน GRU ซ้ำ K รอบด้วยน้ำหนักเดียวกัน (weight-tied) เพิ่ม "ความลึกในการคำนวณ" โดยไม่เพิ่มพารามิเตอร์; any-time = เลือก K ตอนใช้งานได้ ยิ่งรอบมากยิ่งแม่น (ถ้าได้ผล) ตอบเร็วเมื่อ K น้อย.
- **init-normalised weighting:** ตั้งน้ำหนักของ loss สองงานจากขนาด loss ตอนเริ่มเทรน ให้ flow กับ depth มีอิทธิพลเริ่มต้นเท่ากัน แทนการเลือกด้วยมือ.
- **domain shift:** ข้อมูลทดสอบมีการกระจายต่างจากข้อมูลเทรน (Spring GT ช้ากว่า, ฉาก/depth ต่างจาก Sintel).
- **ODE instability:** การวนซ้ำของ recurrent/dynamics ทำให้ error ค่อยโตแบบ exponential ตามเวลา (M1 seed 1: EPE ข้าม 5 ที่ก้าว ~300 แล้วโต ~6.5x ต่อ 10% ของ clip).
- **median alignment:** เทียบ depth หลังเลื่อน log-depth ของ prediction ให้มัธยฐานเท่า GT ต่อ clip เพราะ depth ต่างโดเมนมี scale/offset ต่างกัน (shift เฉลี่ย 3.02 nat-log). ใช้ aligned RMSE เป็นตัวหลักบน Spring.
- **last vs best checkpoint:** last = ตอนจบ 30k iter, best = iter ที่ val ดีสุด (เลือกบน val). Phase 1 ใช้ best; phase 2 ใช้ last เพราะ val ไม่ทำนาย test (r = 0.09). best บน Spring รายงานเป็นรอง (L2).
- **EPE (end-point error):** ระยะระหว่าง flow ทำนายกับ GT (หน่วย: ตาม scale ของข้อมูล lattice); **floor:** baseline ง่าย ๆ (zero-flow, LK, train-mean depth) ที่โมเดลต้องชนะก่อนอ้างว่าเรียนรู้จริง; **ORACLE:** ค่าคงที่ความเร็วที่รู้ GT ไม่ใช่คู่แข่ง; **null model:** wiring ที่รักษาสถิติบางอย่าง (degree) แต่ทำลาย "ใครต่อกับใคร".

## 4. Q&A คำถามยาก (คำตอบสั้นและซื่อสัตย์)

**Q1. ทำไมไม่ชนะ Lucas-Kanade / zero-flow?**
A: งานยากจริงบนข้อมูลที่ train มีแค่ 674 เฟรม และผ่านตาแมลงที่ความละเอียด 721 จุด. Sintel test มีแค่ M5 ที่ชนะ LK (5.253 vs 5.337); Spring ไม่มีเลย (LK 0.4655). Spring GT ช้ามากจน zero-flow ก็เกือบดีที่สุด. เรารายงาน floors เพื่อให้เห็นความจริงนี้.

**Q2. ทำไมใช้ test ใหม่ (Spring) ไม่ใช้ Sintel test เดิมซ้ำ?**
A: Sintel test ถูกใช้ครั้งเดียวใน phase 1 แล้ว (A1-A8); ถ้าใช้ซ้ำเพื่อตัดสินวิธีของเรา จะเป็นการ "ปรับตาม test". Spring เป็น test สดและต่างโดเมน. ผล Sintel ของ phase 2 รายงานเป็น "ดูซ้ำ" L2.

**Q3. ใช้ test ซ้ำไหม?**
A: ไม่ใช้เพื่อเลือกโมเดล: Sintel test ประเมินครั้งเดียวต่อ run ใน phase 1, Spring ครั้งเดียวต่อ run ใน phase 2. กฎ last-checkpoint ตัดสินใน A9 ก่อนเห็นผล Spring. ข้อที่ยอมรับ: ตัวเลข Sintel ของ arm phase 2 เป็น L2.

**Q4. ทำไม Spring flow EPE เล็กมาก (0.5)? ดีมากไหม?**
A: ไม่ได้แปลว่าดี. GT ของ Spring ช้ามาก: zero-flow EPE = 0.4997 คือความเร็ว GT เฉลี่ย. ต้องเทียบกับ floor ไม่ใช่ดูตัวเลขเดี่ยว: ทุกโมเดลที่เรียนรู้ยังแย่กว่า zero-flow.

**Q5. M1 ระเบิดแปลว่าสมองแมลงไม่ดี?**
A: ไม่. เป็น 1 ใน 3 seed ของ M1 ที่เทรน 30k iter และ rollout ยาว (515 ก้าว); seed อื่น 0.527/0.718 และ best.pt ของ seed เดียวกันได้ 0.718. เห็นว่ามีลักษณะ ODE ไม่เสถียร (L3). เราสรุปแค่ "เทรนแบบนี้ไม่เสถียรข้ามโดเมน" ไม่ใช่ประเมินสมองแมลง. ยืนยันแล้วว่าไม่ใช่บั๊ก kernel.

**Q6. ทำไม null (M2/M3) ดีกว่า M1 บน Spring?**
A: เราเห็นว่า null ทายความเร็วต่ำ (~0.44x) ซึ่งได้เปรียบเมื่อ GT ช้า และ M1 ไวต่อ seed/ความยาว clip. สาเหตุเป็นสมมติฐาน (H-a, H-b) ยังไม่ทดสอบ. ช่องว่างเล็กและเทียบ M1 เฉพาะ seed 0,2 ยังแพ้ null (0.623 vs 0.555).

**Q7. ทำไม Ours-L แย่กว่า Ours-S?**
A: Ours-L แย่กว่า Ours-S 21/24 คู่ EPE (0.809 vs 0.590). เห็นว่ามันทายความเร็วเกิน (1.59x vs 0.44x) บน Spring ที่ GT ช้า. ข้อมูลเทรนน้อย โมเดลใหญ่ย้ายโดเมนแย่กว่า (สมมติฐาน H-c). ไม่ได้ปรับ lr/regularisation ของโมเดลใหญ่แยก.

**Q8. Overfit ไหม?**
A: มีสัญญาณ: val ดีสุดที่ ~6k iter แต่เราเทรน 30k เท่ากันทุก arm โดยตั้งใจ (เพื่อความแฟร์). จึงรายงาน last เป็นหลักใน phase 2 และ best เป็นรอง. งานต่อคือ early stop จากหลาย val.

**Q9. Last vs best checkpoint: ทำไมเปลี่ยนกฎ?**
A: เพราะพบว่า val ไม่ทำนาย test (r = 0.09; ชนะ LK val 16/30, test 2/30) จึงเลือกด้วย val ไม่น่าเชื่อ. กฎเปลี่ยนใน A9 ก่อนรัน phase 2 และบอกชัดว่าตัวเลข phase 1 (best) กับ phase 2 (last) เทียบตรงไม่ได้.

**Q10. Scale-invariant loss ไม่ช่วยเพราะอะไร?**
A: เห็นว่าไม่ช่วย (noSI แย่กว่าเพียง 1/3 seed, mean dDepth 0.001) แต่ไม่รู้สาเหตุแน่. ที่เห็น: โมเดลทาย depth แทบคงที่ (bias^2 66%) จึงปัญหาหลักคือ distribution shift ไม่ใช่ scale. Spring ใช้ aligned อยู่แล้ว.

**Q11. 3 seed พอไหม?**
A: ไม่พอสำหรับผลเล็ก: sd บาง arm ใหญ่ (M6 Spring +-0.41, M5 Sintel +-0.185). เราจึงตั้งเกณฑ์เป็น "ชนะ >= 2/3 หรือ 3/3 seed แบบจับคู่" และไม่อ้างผลที่ต่างน้อยกว่า sd. เป็นข้อจำกัดที่บอกในสไลด์ 18 (ข้อจำกัดด้านเวลา/GPU).

**Q12. เปรียบเทียบแฟร์ไหม (พารามิเตอร์, iteration)?**
A: M1, M2, M3 = 15,387; M4, M8, Ours-S = 15,402 (A1 match รวม decoder). ทุก arm ใช้ข้อมูล train เดียวกัน 30k iter, lr 5e-4, batch 4, 3 seed. ข้อยกเว้นที่บอก: M5 (604k) และ Ours-L (274k) ใหญ่กว่า, และไม่ปรับ lr ต่อ arm.

**Q13. เป็น multi-task จริงไหม?**
A: จริง: โมเดลเดียว (shared trunk) ให้ทั้ง flow และ depth, loss รวมสองงาน (น้ำหนัก init-normalised) และรายงานผลแยกงาน (EPE/angular และ RMSE/AbsRel). ข้อควรระวัง: เราไม่ได้ทดสอบว่า multi-task ช่วยแต่ละงานเทียบ single-task (ไม่มี ablation แบบนั้น).

**Q14. เป็น video จริงไหม?**
A: จริง: อินพุต clip 19 เฟรม และโมเดลเป็น recurrent (state ข้ามเฟรม: GRU/dynamics ของ M1). ไม่ได้ทำนายทีละเฟรมอิสระ. Flow ต้องใช้เวลาโดยนิยาม.

**Q15. ทำไมไม่ใช้ CNN/โมเดล SOTA เช่น RAFT?**
A: เป้าหมายคือคำถามด้าน prior ของ connectome ภายใต้ตาแมลง (721 hexal) จึงเทียบกับโมเดลบน lattice เดียวกัน (M4, M5). ไม่ได้อ้างว่าชนะ SOTA บนภาพปกติ. เรามี floor LK บน hex ไว้ calibrate.

**Q16. ทำไมแบ่งข้อมูลตามฉาก?**
A: กัน data leakage: เฟรมติดกันแทบเหมือนกัน. แบ่งตามตระกูลฉาก (seed 20261005). ผลข้างเคียง: test มี 2 ตระกูลฉากเท่านั้นและ val/test ต่างการกระจาย depth มาก.

**Q17. ทำไม depth ไม่มีใครชนะ floor บน Sintel test?**
A: floor คือ train-mean ต่อ hexal ได้ 0.766 เพราะ test log-depth ใกล้ train (0.87 vs 1.14), ไม่ใช่ floor ฉลาด. โมเดลทายเกือบคงที่และมี correlation ภายใน sequence ติดลบ (-0.31). ชนะเฉพาะ bandage แพ้ cave ทุก run (L3).

**Q18. Floor ที่เทียบ แฟร์ไหม (floor ใช้ train mean ตรง ๆ)?**
A: ใช่ มันถูกนิยามในลงทะเบียนก่อนรัน เป็น baseline ที่ไม่ต้องเรียนรู้. ที่ต้องบอกคือ floor บน val ไม่แข็งพอ (1.863) ทำให้ผล val ชวนเข้าใจผิด; จึงรายงานทั้งสอง.

**Q19. Recurrent depth ช่วยจริงไหม?**
A: ภายในโมเดลเดียวบน Sintel ใช่: K1 5.769 -> K4 5.578 ลดทุก seed แต่ผลตอบแทนลดเร็ว และทุก K ยังแย่กว่า M4 (5.411). บน Spring ไม่ช่วยข้ามโดเมน (Ours-S flat 0.580 -> 0.590; M8 แย่ลง). ablation K1 แย่กว่า Ours-S 2/3 seed.

**Q20. M8 K=4 ทำไมแย่กว่า M4 ทั้งที่คำนวณมากกว่า?**
A: H6 ไม่ผ่าน (0/3 seed): M8 5.578 vs M4 5.411 บน Sintel และ 1.670 vs 0.649 บน Spring. การวนซ้ำเพิ่มความไม่เสถียรหากไม่มี EPE loss/น้ำหนักที่ปรับ; ส่วนผสมของ Ours-S แก้ได้บางส่วน (0.590). สาเหตุแน่ชัดยังไม่ทดสอบ.

**Q21. ทำไม hybrid (M6) ดี depth แต่แย่ flow?**
A: H4: RMSE ชนะ M4 3/3 seed (0.857 vs 0.976) แต่ EPE ชนะ 0/3. เกณฑ์ต้องชนะทั้งสองจึงไม่ผ่าน. M6 vs M7 (real vs rewired) EPE 0/3 -> ส่วนดีของ depth ไม่ใช่ของ connectome โดยเฉพาะ (M7 0.859).

**Q22. Real vs rewired หลายอันดูเหมือนกัน แปลว่า null model ไม่ดีพอไหม?**
A: M2 รักษา degree ซึ่งอาจเก็บโครงสร้างสำคัญไว้ (จำนวนสายและชนิดเซลล์); M3 สุ่มทั้งกราฟ ก็ได้ผลใกล้กัน (5.627). การที่ทั้งสองแบบ null เท่ากับ M1 สนับสนุนว่า "ใครต่อกับใคร" ไม่ใช่ปัจจัยหลักในงานนี้ แต่ขอบเขตจำกัดอยู่ที่ตัวชี้วัดและขนาดเทรนของเรา.

**Q23. H3 (data efficiency) ผลเป็นอย่างไร?**
A: ผ่านบางส่วน 2/4 การเปรียบเทียบ (เชิงบรรยาย; รายงานได้ทั้งสองทาง). ตัวอย่าง M1 vs M5 EPE ช่องว่างที่ 25% data ใหญ่กว่า แต่ M1 vs M2 ไม่. ไม่พอสรุปว่า connectome ช่วยเมื่อข้อมูลน้อย.

**Q24. ทำไม M5 ถึงชนะ LK บน Sintel แต่ไม่ใช่บน Spring?**
A: gain ของ M5 บน Sintel 65% มาจาก cave_2 และ sd สูง (+-0.185) ผลจึงเปราะ. Spring เป็นโดเมนต่าง GT ช้า (M5 0.665 > zero 0.4997). เห็นสอดคล้องกับ domain shift.

**Q25. Domain shift: คุณรู้ได้อย่างไรว่าเป็นเหตุ?**
A: ไม่รู้แน่ชัด. ที่เห็นคือความเร็วเฉลี่ย GT ของ Spring (0.50) ต่ำกว่าสิ่งที่โมเดลทาย และ depth shift ต่อ clip ~3 nat-log. เป็นการสังเกต (L3) ไม่ใช่การทดลองควบคุม.

**Q26. Val ไม่สะท้อน test แล้วใช้ val ทำอะไรได้?**
A: ใช้ตรวจว่าเทรนไม่พัง (sanity) และเลือก checkpoint ใน phase 1 (best.pt). แต่ไม่ใช้อ้างผล. เราเสนอ early stop จากหลาย val เป็นงานต่อ.

**Q27. Learning rate เดียวใช้ทุก arm แฟร์ไหม?**
A: เทียบด้วย budget เท่ากัน (ง่ายตรวจสอบ) แต่อาจไม่เหมาะสุดต่อ arm และอาจเอื้อบาง arm. เป็นข้อจำกัดที่เปิดเผย; ถ้ามีเวลาจะปรับ lr ต่อ arm.

**Q28. Ours-S ชนะ M4 3/3 seed แต่ P2 ไม่ผ่าน ทำไม?**
A: P2 กำหนดให้ชนะทั้ง flow และ aligned depth >= 2/3 seed. Flow 3/3 แต่ depth 1/3 -> ไม่ผ่านทั้งงาน. เรารายงานทั้งสองส่วน ไม่เลือกเล่นส่วนเดียว.

**Q29. ทำไม Ours-S ไม่ชนะ null (M2/M3) บน flow?**
A: ไม่ชนะจริง: 0.590 vs 0.555/0.574 และ M2/M3 ชนะรายคู่ 16/24 คู่ (seed x sequence). ช่องว่างเล็ก (L3). วิธีของเราดีสุดในกลุ่ม deep learning ขนาดเท่ากันเท่านั้น.

**Q30. คุณเลือก 8 sequence ของ Spring ได้ไหม มี cherry-pick ไหม?**
A: เลือกด้วย seed 20261010 ก่อนดูเนื้อหา บันทึกใน `spring_sequences.json`. ตัวอย่างภาพ (สไลด์ 13) เลือก post hoc และบอกไว้.

**Q31. Sequence เดียว (0033) ครองผลหรือไม่?**
A: ใช่ในแง่ error: 7% ของ hexal แต่ 47% ของ zero-flow EPE. จึงมี per-sequence (สำรอง B). M2/M3 ชนะรายคู่ แต่ไม่มี arm ชนะ zero เกิน 1/8 sequence.

**Q32. Error analysis เชื่อได้แค่ไหน?**
A: ทั้งหมด L3 (exploratory) ยกเว้นตัวชี้วัดหลักที่ลงทะเบียน. คำอธิบายเป็นสมมติฐาน. ความเร็วทำนายเป็นค่าประมาณจาก (|GT|, EPE, มุม).

**Q33. ผลของคุณ generalize ไปสมองจริง/ธรรมชาติได้ไหม?**
A: ไม่อ้าง. เราทดสอบ prior ในโมเดลเชิงคำนวณบน 2 ชุดวิดีโอ synthetic/สังเคราะห์ (Sintel เป็นแอนิเมชัน, Spring เป็น render). ไม่ได้สรุปเรื่องชีววิทยา.

**Q34. ผลนี้ขัดกับงาน flyvis (Lappalainen 2024) ไหม?**
A: ไม่จำเป็น: ต่างงานและเกณฑ์. เราถามว่า wiring จริงเหนือ wiring สลับ/ConvGRU ขนาดเท่ากันบน flow+depth ที่เทรนใหม่จากศูนย์ข้อมูลน้อยไหม. ไม่ได้ทดสอบ flyvis pretrained ใน grid หลัก (M0 เคยเห็นฉาก test บางฉาก จึงไม่ใช้ตัดสิน; A3).

**Q35. ใช้ AI ช่วยไหม?**
A: ใช่ ใช้ AI coding assistants ช่วยเขียนโค้ดบางส่วน ภายใต้การตรวจโดยคน (code review) และ unit tests; ประวัติการทำงานดูได้ใน git log. สมมติฐาน การออกแบบการทดลอง และการตีความผลเป็นของกลุ่ม และสมาชิกแต่ละคนอธิบายส่วนของตนได้.

**Q36. ผลทั้งหมดทำซ้ำได้ไหม?**
A: มี seed, config และสคริปต์ใน repo; ตัวเลขสร้างจาก `results/summary.csv`/`summary_p2.csv`; per_pixel.npz เก็บไว้. ข้อควรระวัง: fused kernel เทียบ parity ~1e-7 และ M1 seed 1 ซ้ำได้เมื่อไม่ใช้ fused kernel.

**Q37. ถ้ามีเวลาเพิ่มจะทำอะไร?**
A: (1) ตรวจสาเหตุ M1 ไม่เสถียร (เช่น clip gradient/ลด rollout ยาว), (2) ปรับ lr ต่อ arm และเทรนนาน/ข้อมูลมากขึ้นพร้อม early stop จากหลาย val, (3) split แบบ stratify ตามระยะลึก, (4) depth head ที่ calibrate ข้ามโดเมน, (5) seed มากกว่า 3 สำหรับผลเล็ก.

**Q38. ข้อสรุปเดียวที่อยากให้จำ?**
A: wiring จริงของสมองแมลงไม่ดีกว่า wiring สลับในงานนี้ (L1) และ pre-registration + floors + null + test ครั้งเดียว ทำให้เรารู้ได้โดยไม่หลอกตัวเอง.

**Q39. ทำไมคะแนนความยาก "multi-task/video" ถึงควรได้ 4?**
A: โมเดลเดียวเรียนรู้ 2 งาน (flow, depth) รายงานแยก และใช้ความสัมพันธ์ข้ามเฟรม (recurrent) ตามเงื่อนไขในเกณฑ์; มีผลประเมินบน test ที่แยกไว้ 2 ชุด.

**Q40. ทำไมใช้ median alignment กับ depth ของ Spring ไม่ใช่ Sintel?**
A: Spring ต่างโดเมนมี scale/offset ของ depth ต่าง (shift เฉลี่ย 3.02 nat-log) ซึ่งโมเดลที่เทรนบน Sintel ทายไม่ได้ เรียกได้ว่าเป็นการวัด "รูปร่างสัมพัทธ์". Raw RMSE รายงานรอง. Floor ก็ aligned ด้วยกฎเดียวกัน (0.9362) จึงเทียบแฟร์.
