### สไลด์ 2: question, คำถามของเรา (#8)
**พูดอะไร:** คำถามเดียวของงานนี้คือ wiring จริงจากสมองแมลงหวี่ ช่วยให้โมเดลเรียนรู้ได้ดีขึ้นหรือใช้ข้อมูลน้อยลงไหม ภาพเล็ก ๆ ด้านข้างคือ wiring จริงเทียบกับ wiring ที่สลับสายแล้ว ถ้าโครงสร้างจริงมีข้อมูลอยู่ โมเดลจริงต้องชนะโมเดลที่สลับสาย เรากำหนดสมมติฐานไว้ล่วงหน้าและจะรายงานตามจริงไม่ว่าผลจะออกทางไหน
**ประเด็นต้องจำ:**
- "ช่วย" แปลเป็นสิ่งวัดได้ 2 แบบ: ผลดีกว่าที่พารามิเตอร์เท่ากัน (H1, H2) และใช้ข้อมูลน้อยแล้วช่องว่างกว้างขึ้น (H3, ที่ 25% ของ train)
**ระวัง:** นี่เป็นคำถาม ไม่ใช่ข้อสรุป; ห้ามพูดว่า "connectome ดีกว่า"

### สไลด์ 3: why, ทำไมตอนนี้ (#2)
**พูดอะไร:** ปี 2024 มีสองเหตุการณ์ คือ FlyWire connectome ของสมองแมลงหวี่ทั้งสมอง (Dorkenwald et al., Nature 2024) และ flyvis ของ Lappalainen et al. (Nature 2024) ที่สร้างโครงข่ายจาก connectome แล้วทำนาย motion ได้ เราเอาโครงข่ายนี้มาแข่งกับ deep learning ปกติบนงาน multi-task video ซึ่ง flyvis ที่ train มาให้ทำ flow อย่างเดียว
**ประเด็นต้องจำ:**
- connectome = แผนผังว่าเซลล์ประสาทต่อกับใคร; flyvis = connectome-constrained network
- flyvis ในเปเปอร์ train flow อย่างเดียว 250k iteration
**ระวัง:** อย่าอ้างว่าเรา "ทำซ้ำ" เปเปอร์; เราใช้โค้ด flyvis เป็นเครื่องมือและตั้งคำถามใหม่

### สไลด์ 4: task, งาน Multi-task Video (#8)
**พูดอะไร:** input คือวิดีโอ 19 เฟรมที่ render เป็นภาพจากตาแมลง 721 hexal จากนั้นผ่านโมเดลที่เป็น recurrent จำข้อมูลข้ามเวลา แล้วมี 2 head คือ optic flow (u,v) ต่อ hexal และ depth ต่อ hexal โมเดลตัวเดียวทำทั้งสองงานพร้อมกัน เรารายงานผลแยกแต่ละงาน งานนี้เข้าเกณฑ์ความยาก 4 คะแนน เพราะเป็นทั้ง multi-task และ video
**ประเด็นต้องจำ:**
- 19 เฟรม, 50 Hz (dt = 0.02 s), 721 hexal
- shared trunk + 2 heads, loss ต่องานถ่วงเท่ากัน
- video จริง: flow นิยามได้เฉพาะระหว่างเฟรม โมเดลมี recurrent state
**ระวัง:** ยังไม่มีผลที่พิสูจน์ว่าได้ 4 คะแนน เกณฑ์ต้องมีโมเดลทำงานจริง + ผลประเมิน ซึ่งผลบน test จะมาหลัง grid

### สไลด์ 5: eye, ตาแมลงหวี่ = ตาข่ายหกเหลี่ยม (#1)
**พูดอะไร:** ตาแมลงหวี่ไม่ใช่พิกเซลสี่เหลี่ยม แต่เป็นตาข่ายหกเหลี่ยม เราใช้รัศมี 15 รวม 721 hexal ภาพ Sintel ถูก render ลงตาข่ายนี้ด้วยโค้ดของ flyvis ดังนั้นความละเอียดต่ำกว่าภาพต้นฉบับมาก แต่ทุกโมเดลเห็น input เดียวกันหมด
**ประเด็นต้องจำ:**
- 721 hexal; box filter (extent 15, kernel 13); `vertical_splits=3` ทำให้ 1 เฟรมเป็น 3 มุมมอง
- 1 hexal มีเพื่อนบ้าน 6 ทิศ (convolution ใช้ 7 จุดรวมตัวเอง)
**ระวัง:** เทียบกับ leaderboard Sintel ตรง ๆ ไม่ได้ (ความละเอียดต่ำมาก)

### สไลด์ 6: data, MPI Sintel + แบ่งตามตระกูลฉาก (#1)
**พูดอะไร:** ข้อมูลคือ MPI Sintel (Butler et al. 2012) pass "final" ที่มี ground truth ทั้ง flow และ depth ทุกพิกเซล มี 23 ฉาก 1,064 เฟรม เราแบ่งตามตระกูลฉาก เพราะ Sintel มีหลายฉากตัดจากฉากต้นทางเดียวกัน เช่น ambush_2 ถึง ambush_7 ถ้าสุ่มรายเฟรมภาพเกือบเหมือนกันจะรั่วข้ามชุด มีเทสต์อัตโนมัติยืนยันว่าไม่รั่ว และ augmentation ใช้เฉพาะ train
**ประเด็นต้องจำ:**
- train 15 ฉาก 674 เฟรม (alley, ambush, bamboo, shaman, sleeping, temple) · val 4 ฉาก 190 (market, mountain) · test 4 ฉาก 200 (bandage, cave) · รวม 23 ฉาก 1,064 เฟรม
- split seed คงที่ 20261005, ไฟล์ `splits.json`
- depth: log + clip + standardize ด้วยสถิติ train เท่านั้น
- augmentation: flip/rotation บน hex, contrast, brightness, noise, temporal crop; val/test ไม่มี
**ระวัง:** test มีแค่ 2 ตระกูลฉาก (bandage, cave) เป็นข้อจำกัด; ชุดทางการของ Sintel ไม่มี GT จึงไม่ได้ใช้

### สไลด์ 7: lineup, 8 แบบจำลองที่จะเปรียบเทียบ (#2 + #4)
**พูดอะไร:** (#2) กลุ่มแรกคือ connectome: M1 wiring จริง, M2 สลับสายแบบรักษา degree, M3 สุ่ม ทั้งสามมี 15,387 พารามิเตอร์ ในนั้นเป็นตัวโครงข่าย 734 (#4) กลุ่ม deep learning: M4 HexConvGRU ขนาดเท่า M1 (15,402) กับ M5 ตัวใหญ่ 604,835 กลุ่ม hybrid M6/M7 และแบบ frozen+residual M6f/M7f กับ M8 HexConvGRU-K รวมทุกแบบรัน 3 seed เป็น 39 รอบ
**ประเด็นต้องจำ:**
- M1-M3 = 15,387 (734 network + 14,653 decoders) · M4 = 15,402 (+0.1%) · M5 = 604,835 (~40x) · M6/M7 = 15,423 · M6f/M7f trainable 14,689 · M8 = 15,402
- 39 รอบ = 24 (M1-M5 x 3 seed + data-efficiency arm 25%: M1, M2, M5) + M6/M7 (6) + M6f/M7f (6) + M8 (3)
- ทุกโมเดล: input เดียว, loss เดียว, optimizer/iteration/batch เท่ากัน (30k iter, batch 4, lr 5e-4)
**ระวัง:** M5 ตั้งใจให้ใหญ่กว่า ไม่ใช่การเปรียบเทียบพารามิเตอร์เท่ากัน; M0 (flyvis pretrained) เป็นแค่อ้างอิง ไม่ได้ train โดยเรา

### สไลด์ 8: nulls, Null model (#3)
**พูดอะไร:** ถ้า M1 ดี เราไม่รู้ว่าดีเพราะ "ใครต่อกับใคร" หรือแค่เพราะมีจำนวนสายและสถิติแบบนี้ เลยทำ null model สองแบบ M2 สลับปลายทางด้วยวิธี Maslov-Sneppen เก็บ in/out degree เครื่องหมาย และ kernel เชิงพื้นที่ไว้ แต่เปลี่ยนว่าใครต่อกับใคร M3 สุ่มแบบ Erdős-Rényi เก็บแค่จำนวนเส้นและสัดส่วน E/I ถ้า M1 ชนะ M2 ข้อมูลอยู่ที่รูปแบบการเชื่อมต่อจริง
**ประเด็นต้องจำ:**
- ระดับชนิดเซลล์: 604 คู่ชนิดเซลล์ (65 ชนิด); M3 สัดส่วน 376 กระตุ้น : 228 ยับยั้ง
- connectome จริงมี self-loop ภายในชนิดเดียว 23 เส้น แต่ M2 ไม่มี (ข้อสังเกตที่ต้องรายงาน)
- M3 ไม่มีเส้นเข้า photoreceptor R1-R8
**ระวัง:** M2 คุมได้เฉพาะที่ระดับ type-graph ไม่ได้บอกว่าเป็น null ที่สมบูรณ์ทุกมิติ

### สไลด์ 9: hybrid, Hybrid connectome เป็น front-end (#4)
**พูดอะไร:** เพราะ probe บอกว่า M4 ชนะ M1 เราเลยเพิ่ม hybrid: ใช้ connectome เป็นด่านแรก ส่ง activity ของ 34 output cell types บน 721 hexal เข้า HexConvGRU trunk แล้วออก flow/depth (M6) แถวที่สอง M6f ใช้ M1 ที่ train แล้วแช่แข็ง บวก residual ที่ layer สุดท้ายเริ่มเป็น 0 จึงเริ่มที่คำตอบของ M1 พอดี ส่วน M7/M7f ใช้ connectome สลับสายเป็น control
**ประเด็นต้องจำ:**
- เพิ่มใน amendment A5/A6 **หลังเห็น probe แต่ก่อน grid** เปิดเผยไว้ใน PLAN.md
- M6/M7 15,423 params; M6f/M7f trainable 14,689
- control ตอบ: ประโยชน์มาจาก wiring หรือแค่มี recurrent front-end เพิ่ม
**ระวัง:** พูดตรง ๆ ว่าเพิ่มหลัง probe; อย่าทำเหมือนวางแผนตั้งแต่ต้น. 34 = จำนวน output cell types ของ connectome flyvis (ตรวจจากโค้ดแล้ว: `len(network.connectome.output_cell_types)`)

### สไลด์ 10: metrics, วัดผลอย่างไร (#6)
**พูดอะไร:** flow วัดด้วย EPE (ระยะเวกเตอร์ที่ทำนายกับจริง) และ angular error (องศา) depth วัดด้วย RMSE บน log-depth ที่ normalize แล้ว และ AbsRel บน depth จริง กติกามี 3 ข้อ เลือก hyperparameter บน val, ประเมิน test ครั้งเดียว โค้ดล็อกไว้, รายงาน mean ± sd จาก 3 seed
**ประเด็นต้องจำ:**
- EPE = mean ‖(u,v)_pred − (u,v)_gt‖₂ · AbsRel = mean(|pred−gt|/gt) บน depth จริง (clip 0.19-2,522)
- `eval.py` ไม่ยอมรันซ้ำบน test ถ้าไม่ใส่ `--force` และต้องบันทึกเหตุผล
- เปรียบเทียบแบบจับคู่ seed (paired)
**ระวัง:** รายงานแยกสองงาน ไม่รวมเป็นคะแนนเดียว

### สไลด์ 11: floors, ต้องชนะอะไรถึงจะเรียกว่าเรียนรู้ (#6)
**พูดอะไร:** ก่อนบอกว่าโมเดลเรียนรู้ ต้องชนะเส้นฐานที่ไม่ต้อง train บน val: zero-flow 5.074, train-mean 5.288, Lucas-Kanade บนตาข่ายหกเหลี่ยม 4.709 ซึ่งเป็นวิธีคลาสสิกที่มี calibration 4 พารามิเตอร์ fit บน train ส่วน oracle constant-velocity 1.316 ใช้ GT เฟรมก่อน จึงไม่ใช่คู่แข่ง ใส่ไว้ให้เห็นว่าเพดานของ "เดาจากเฟรมก่อน" อยู่ตรงไหน เราจะรายงานเป็น margin เหนือ floor ที่ดีที่สุดที่ไม่ใช่ oracle
**ประเด็นต้องจำ:**
- flow val EPE: zero 5.074 · train-mean 5.288 · LK 4.709 · oracle 1.316 (ยิ่งต่ำยิ่งดี)
- depth val RMSE: train-mean 1.863 · per-hexal train-mean 1.856
- LK: window/lambda จูนบน val; ไม่เรียนรู้ด้วย gradient
- ลงทะเบียน floors ไว้ก่อน grid (A6.1); รายงานบน test ด้วย `floors.py --split test --once`
**ระวัง:** ตัวเลขนี้เป็น val ไม่ใช่ test; oracle ห้ามเรียกว่า baseline ที่ต้องชนะ

### สไลด์ 12: hypotheses, สมมติฐาน (ลงทะเบียนก่อน train) (#8)
**พูดอะไร:** เราเขียนสมมติฐาน H1-H7 ไว้ก่อน train: H1 M1 ชนะ M2 ทั้งสองงานทุก seed, H2 M1 ชนะ M4, H3 ที่ข้อมูล 25% ช่องว่างกว้างขึ้น, H4 M6 ชนะ M4, H5 M6 ชนะ M7 3/3 seed, H6 M8 K=4 ชนะ M4 อย่างน้อย 2/3 seed, H7 M6f ชนะ M7f 3/3 seed ผลจะรายงานตามจริงไม่ว่าออกทางไหน
**ประเด็นต้องจำ:**
- H1-H3 ลงทะเบียน 2026-10-05; H4-H5 (A5) และ H6-H7 (A6) เพิ่ม 2026-10-08 ก่อน grid
- H3 เป็น descriptive (รายงานทั้งสองทิศทาง)
- H1 ต้อง 3/3 paired seed บน test; H4 ต้องชนะค่าเฉลี่ย และ ≥ 2/3 paired seed
**ระวัง:** H4-H7 ลงทะเบียนหลังเห็น probe (แต่ก่อน grid); H2 มีสัญญาณเตือนแล้วว่าอาจไม่จริง

### สไลด์ 13: probe, ผลเบื้องต้น learnability probe (#5)
**พูดอะไร:** ก่อนรัน grid ทั้งหมด เราลงทะเบียน probe ไว้ก่อน (A4): M1 กับ M4 seed 0, 10k iteration, lr 5e-4 เกณฑ์ผ่านคือมีโมเดลใดโมเดลหนึ่งได้ val EPE ≤ 4.97 ผลคือผ่าน M1 ดีสุด 4.915, M4 ดีสุด 4.501 เทียบ zero-flow 5.074 เลยคง flow บน Sintel ไว้ แต่ต้องพูดตรง ๆ ว่า M4 ชนะ M1 และ Lucas-Kanade 4.709 ก็ชนะ M1 ที่ 10k นี่เป็นสัญญาณเตือนว่า H2 อาจไม่จริง
**ประเด็นต้องจำ:**
- M1 ดีสุด 4.915 (iter 9k, -3.1%) · M4 ดีสุด 4.501 (iter 6k, -11.3%) · EPE ที่ 10k: M1 4.982, M4 4.666
- เกณฑ์ PASS ≤ 4.97 (≥ 2% ต่ำกว่า zero-flow); ถ้า FAIL มีแผนสำรอง (synthetic motion, masked flow, lower-res)

**พูดอะไร:** การรัน 39 รอบต้องเร็วพอ เราจึงเร่งความเร็ว M1 จาก 0.202 เป็น 0.074 s/iter (2.7 เท่า) ด้วย fastfly ซึ่งเป็น Triton fused kernel; M4 จาก 0.138 เป็น 0.027 (5 เท่า) ด้วย torch.compile; M5 จาก 0.73 เป็น 0.19 (3.8 เท่า) mixed precision ไม่ช่วย (ไม่เกิน 4%) grid ทั้งหมดประมาณ 31-35 ชั่วโมงบนเครื่องเดียว

## 3. ความรู้ที่ทุกคนต้องรู้ (glossary)
- **connectome:** แผนผัง wiring ว่าเซลล์ประสาทแต่ละเซลล์ต่อกับใคร (FlyWire = ทั้งสมองแมลงหวี่)
- **flyvis / connectome-constrained network:** โครงข่ายที่โครงสร้าง (ใครต่อใคร, เครื่องหมาย, kernel เชิงพื้นที่) ถูกกำหนดจาก connectome เหลือปรับได้แค่ค่า (bias, time constant, strength ต่อคู่ชนิดเซลล์) = 734 พารามิเตอร์; 45,669 เซลล์, 65 ชนิด, 604 คู่ชนิดเซลล์
- **hexal:** หนึ่งจุดบนตาข่ายหกเหลี่ยมของตา (721 จุด)
- **optic flow:** เวกเตอร์ (u,v) ต่อจุด บอกว่าภาพจุดนั้นเคลื่อนไปทางไหนระหว่างเฟรม
- **EPE (End-Point Error):** ระยะ Euclidean ระหว่างเวกเตอร์ flow ที่ทำนายกับจริง เฉลี่ยทุก hexal/เฟรม
- **angular error:** มุมระหว่าง (u,v,1) ที่ทำนายกับจริง (องศา)
- **RMSE / AbsRel:** RMSE = √mean((d_pred−d_gt)²) บน log-depth ที่ standardize; AbsRel = mean(|pred−gt|/gt) บน depth จริง
- **null model:** โมเดลควบคุมที่คงคุณสมบัติบางอย่างไว้ แต่ทำลายสิ่งที่เราสนใจ (ใครต่อกับใคร) ไว้เทียบ
- **degree-preserving rewiring:** สลับปลายเส้นเชื่อมแบบ Maslov-Sneppen ให้จำนวนเส้นเข้า/ออกของแต่ละชนิดเซลล์ เครื่องหมาย และ kernel คงเดิม
- **ConvGRU:** GRU ที่ใช้ convolution (ที่นี่คือ hex convolution) แทนการคูณเมทริกซ์ จำสถานะข้ามเฟรม
- **multi-task:** โมเดลเดียวเรียนหลายงานพร้อมกัน (flow + depth) และรายงานแยกงาน
- **pre-registration:** เขียนสมมติฐานและเกณฑ์ตัดสินไว้ก่อนรัน (PLAN.md + amendments)
- **floor:** เส้นฐานที่ไม่ต้อง train (zero-flow, train-mean, LK) ที่โมเดลต้องชนะจึงจะเรียกว่าเรียนรู้
- **Lucas-Kanade (LK):** วิธีคลาสสิกประมาณ flow จากการไล่ระดับความสว่างในหน้าต่างเล็ก ๆ; ของเราทำบน hex lattice + calibration 4 พารามิเตอร์ (แผนที่หน่วย 2x2) fit บน train
- **oracle:** ตัวอ้างอิงที่แอบใช้ GT (ที่นี่ใช้ flow จริงเฟรมก่อน) บอกเพดาน ไม่ใช่คู่แข่ง
- **claim ladder L1-L3:** L1 = pre-reg + test · L2 = pre-reg แต่ val/ไม่ครบ · L3 = exploratory
- **CKA:** วัดความคล้ายของ representation ระหว่างสองโมเดล (Kornblith 2019)
- **divergence/curl:** ตัวดำเนินการบน flow field; divergence สูง = ขยายออก (looming), curl = หมุน
- **Triton kernel / torch.compile:** Triton = เขียน GPU kernel ด้วย Python (fastfly ใช้ fuse หลายขั้นเป็นรอบเดียว); torch.compile = ให้ PyTorch รวมและเร่งกราฟอัตโนมัติ
- **test-once:** ประเมินบน test ครั้งเดียวหลังตัดสินใจทุกอย่างบน val

## 4. ถามตอบ (Q&A)

### โจทย์และเกณฑ์
**Q1. ทำไมถึงบอกว่าเป็นงาน 4 คะแนน?**
A: เกณฑ์ 4 คะแนนคือ Multi-task หรือ Video เราเข้าทั้งสอง: โมเดลเดียวเรียน flow + depth พร้อมกัน และใช้ recurrent ข้ามเฟรม แต่ต้องมีโมเดลทำงานจริงและผลประเมินด้วย ซึ่งผลบน test จะมาหลัง grid จบ

**Q2. Multi-task จริงไหม หรือแค่เทรนสองโมเดล?**
A: จริง โมเดลเดียวมี trunk ร่วมและ 2 head (flow, depth) รับ loss ต่องานถ่วงเท่ากัน รายงานผลแยกงาน การเปรียบเทียบหลายโมเดลไม่ใช่ตัว multi-task

**Q3. Video จริงไหม หรือทำนายทีละเฟรม?**
A: จริง input เป็นลำดับ 19 เฟรม flow ต้องใช้ความต่างข้ามเฟรม และโมเดลเป็น recurrent (leaky integrator ใน M1, ConvGRU ใน M4) ไม่ได้ทำทีละเฟรมอิสระ

**Q4. ทำไมไม่ใช้ CNN ธรรมดาบนภาพปกติ?**
A: เราใช้ HexConvGRU บนตาข่ายเดียวกันเป็น baseline ทุกโมเดลเห็น input เดียวกัน การเปรียบเทียบจึงตรงคำถามเรื่อง wiring

### ข้อมูล
**Q5. แบ่ง split อย่างไร และกัน leakage อย่างไร?**
A: แบ่งตามตระกูลฉาก (ฉากจากต้นทางเดียวกันอยู่ชุดเดียวกัน) seed 20261005; train 15 ฉาก 674 เฟรม, val 4 ฉาก 190, test 4 ฉาก 200; มีเทสต์ใน `tests/` ว่าไม่ซ้ำข้ามชุด

**Q6. ทำไมไม่สุ่มรายเฟรม?**
A: เฟรมติดกันแทบเหมือนกัน test จะง่ายเกินจริง (data leakage)

**Q7. ทำไมเลือก Sintel?**
A: มี GT ของทั้ง flow และ depth ทุกพิกเซลในชุดเดียวกัน และ flyvis มีตัว render ลงตาข่ายหกเหลี่ยมให้ ทำให้เทียบกับงานต้นฉบับได้

**Q8. ข้อมูลเล็กไป (674 เฟรม) ไหม?**
A: เล็กจริง เป็นข้อจำกัดและเป็นเหตุผลที่คำถาม "prior แทนข้อมูลได้ไหม" น่าสนใจ; ชุด test มีแค่ 2 ตระกูลฉาก จึงควรระวังการสรุปกว้าง

**Q9. Augmentation รั่วไหม?**
A: ใช้เฉพาะ train; val/test ไม่มี augmentation

### โมเดล
**Q10. ทำไมพารามิเตอร์ต่างกันระหว่างโมเดล?**
A: M1-M4, M6-M8 ตั้งใจให้ ~15.4k เท่ากัน (M4 15,402 vs M1 15,387 รวม decoder, ตาม A1); M5 ใหญ่ (604,835) ตั้งใจ เพื่อดูว่าเพิ่มพารามิเตอร์ชนะ prior ไหม; M6f/M7f trainable 14,689

**Q11. ทำไมนับพารามิเตอร์รวม decoder?**
A: ตอนแรกตั้งเป้า 3-6k (นับแค่ network) ซึ่งไม่เป็นธรรมกับ M4 จึงแก้เป็นนับรวม decoder (A1) บันทึกไว้ก่อนรัน

**Q12. ทำไม M5 ใหญ่ขนาดนั้น?**
A: ตอบว่า deep learning ทั่วไปที่มีพารามิเตอร์ ~40 เท่าจะชนะ connectome prior ไหม และใช้ข้อมูลมากกว่าแค่ไหน เป็นการเทียบ compute/พารามิเตอร์ ไม่ใช่การเทียบเท่ากัน

**Q13. ทำไมต้องมี null model?**
A: ถ้าไม่มี M2/M3 เราบอกไม่ได้ว่า M1 ดีเพราะ wiring จริงหรือเพราะแค่โครงสร้างแบบ flyvis ถ้า M1 ชนะ M2 ข้อมูลอยู่ที่ "ใครต่อกับใคร"

**Q14. Hybrid เพิ่มทีหลังเพราะอะไร?**
A: ตอบตรง ๆ: เพิ่มหลังเห็นผล probe ที่ M4 ชนะ M1 แต่ก่อนรัน grid และเปิดเผยไว้ใน PLAN.md A5 (ระบุว่า post-probe) ควบคุมด้วย M7/M7f (rewired) เพื่อแยก wiring ออกจากการมี recurrent front-end

**Q15. ทำไม M6f/M7f เริ่มที่ 0?**
A: layer สุดท้ายของ residual เป็น zero-init ดังนั้นตอนเริ่ม output เท่ากับ M1/M2 ที่ freeze แล้วพอดี จะไม่แย่ลงกว่าจุดเริ่ม ณ ตอน train

**Q16. M1 มีแค่ ~700 พารามิเตอร์ เรียนรู้ได้อย่างไร?**
A: โครงสร้างถูกกำหนดแล้ว เหลือปรับ bias, time constant, strength ต่อคู่ชนิดเซลล์ (734) บวก decoder 14,653 ที่ทำ flow/depth

### การประเมิน
**Q17. ทำไมต้องมี floor?**
A: เพราะ flow บนตาข่ายนี้ยากมาก (flyvis เต็ม 250k iter ชนะ zero-flow ~4%) ต้องมีเส้นฐานบอกว่าโมเดลเรียนรู้จริงหรือแค่ "เดา 0"

**Q18. Oracle คืออะไร? ทำไมไม่นับเป็นคู่แข่ง?**
A: oracle constant-velocity ใช้ GT flow ของเฟรมก่อนหน้า ซึ่งโมเดลจริงไม่มี จึงเป็นเพดานอ้างอิง (val EPE 1.316) ไม่ใช่เส้นที่ต้องชนะ

**Q19. LK calibration 4 พารามิเตอร์ fit บนอะไร? โกง test ไหม?**
A: fit แผนที่หน่วย 2x2 บน train; window/lambda จูนบน val; test ไม่ถูกใช้ ลงทะเบียน floors ก่อน grid

**Q20. ทำไมประเมิน test ครั้งเดียว?**
A: ถ้าดู test หลายรอบแล้วปรับตาม เท่ากับจูนบน test; `eval.py` บล็อกการรันซ้ำถ้าไม่ใส่ `--force` (และต้องบันทึกเหตุผล)

**Q21. 3 seed พอไหม?**
A: ไม่ใช่หลักฐานทางสถิติหนักแน่น งบเวลาจำกัด จึงใช้เกณฑ์แบบ paired (เช่น 3/3 seed) รายงาน mean ± sd และไม่อ้างนัยสำคัญทางสถิติเกินไป

**Q22. ทำไมรายงานสอง metric ต่อ flow และ depth?**
A: EPE เป็นมาตรฐาน Sintel + angular error ดูทิศทาง; RMSE (log-depth) กับ AbsRel (depth จริง) เป็นมาตรฐานงาน depth

### ผลเบื้องต้น
**Q23. M4 ชนะ M1 แปลว่าอะไร?**
A: ใน probe (seed เดียว, val, 10k iter) M4 ได้ 4.501 ต่ำกว่า M1 4.915 แปลว่าที่งบเล็กนี้ M1 ยังไม่ชนะ M4 แต่ยังสรุปไม่ได้ ต้องรอ 3 seed 30k iter บน test; เป็นสัญญาณเตือนว่า H2 อาจไม่จริง

**Q24. ถ้า H ไม่จริง จะทำอย่างไร?**
A: รายงานตามจริง ผลลบมีค่า เพราะลงทะเบียนไว้ล่วงหน้า และใช้ null controls กับ hybrid (H4-H7) บอกว่า wiring ช่วยหรือไม่ช่วยตรงไหน

**Q25. Probe ผ่านแล้วแปลว่าโมเดลดีไหม?**
A: ไม่ ผ่านแค่เกณฑ์ว่า flow เรียนรู้ได้ (≤ 4.97) เพื่อตัดสินว่าคง Sintel flow ไว้; ไม่ใช่การทดสอบสมมติฐาน

### Engineering
**Q26. ทำไมไม่ใช้ Rust ทั้งหมด?**
A: เลือกเครื่องมือตามผล profile: M4/M5 เร็ว 5x ด้วย torch.compile ไม่ต้อง Rust; M1 คอขวดคือ sparse gather/scatter ซึ่ง Triton kernel แก้ได้ 2.4x; เวอร์ชัน Rust ยังไม่ได้สร้าง ประเมินว่า headroom น้อย

**Q27. Triton เร็วขึ้นเพราะอะไร?**
A: รวมหลายขั้น (gather, relu, mul, segment-sum, Euler) เป็นรอบเดียวต่อ ODE step จึงอ่านอาร์เรย์ edge ครั้งเดียว (เดิมหลาย kernel ที่ memory-bound) และเขียน backward เอง

**Q28. ผลเหมือนเดิมไหม (parity)?**
A: ตรวจแล้ว: output ต่างกันประมาณ 1e-7 relative, gradient ~4e-7 relative, loss หลัง train เหมือนกัน ~1e-7; มีเทสต์ใน `tests/test_fastfly.py`

**Q29. ทำไม mixed precision ไม่ช่วย?**
A: วัดแล้ว bf16/tf32 ได้ไม่เกิน 4% เพราะ M1 เป็น memory-bound ไม่ใช่ compute-bound

### ข้อจำกัดและ AI
**Q30. ข้อจำกัดของงานคืออะไร?**
A: ข้อมูลน้อย (674 เฟรม), test มี 2 ตระกูลฉาก, train น้อยกว่าเปเปอร์มาก (30k เทียบ 250k iteration), ไม่ได้จูน lr ต่อโมเดล (ใช้ 5e-4 เท่ากัน), ตาข่าย 721 จุดความละเอียดต่ำ, 3 seed, probe เป็น seed เดียวบน val

**Q31. ใช้ AI ช่วยเขียนโค้ดไหม?**
A: ใช้จริง ใช้ AI coding assistants ช่วยเขียนโค้ด มีการตรวจ มีเทสต์ (เช่น 47 เทสต์ผ่านบน CPU) และมีประวัติใน git log และ `docs/agy` ตรวจสอบย้อนหลังได้ และแต่ละคนต้องอธิบายส่วนที่ตนรับผิดชอบได้

**Q32. เทียบกับ Sintel leaderboard ได้ไหม?**
A: ไม่ได้ ใช้ความละเอียดตาแมลง 721 จุด และชุด test เป็นส่วนของ training ที่เราแบ่งเอง

## 5. คำตอบสำรองเมื่อไม่รู้
สูตร: **ยอมรับ → บอกสิ่งที่รู้ → บอกว่าจะหาที่ไหน → ไม่เดา**
- "ขอบคุณสำหรับคำถามครับ/ค่ะ ส่วนนี้เรายังไม่ได้วัด/ยังไม่มีผล ณ ตอนนี้ สิ่งที่เรารู้คือ [ข้อเท็จจริงที่แน่ใจ] ส่วนที่เหลือจะอยู่ในผล test ที่เราจะรายงาน"
- ถ้าเกี่ยวกับผล test: "ตอนนี้ยังไม่มีผล test เพราะประเมินครั้งเดียวหลัง grid จบ ที่มีคือ val ของ probe seed เดียว"
- ถ้าเกี่ยวกับรายละเอียดโค้ด: "ขอเปิดไฟล์ [ชื่อไฟล์] ยืนยันก่อน/ให้เพื่อนที่รับผิดชอบส่วนนั้นตอบ"
- ถ้าถูกถามเกินขอบเขต (เช่น ชีววิทยาลึก): "เราใช้ connectome ผ่าน flyvis เป็นเครื่องมือ รายละเอียดทางประสาทวิทยาเกินที่เราอ้างได้ ต้นฉบับคือ Lappalainen et al. 2024"
- ถ้าถูกท้วงว่ามีจุดอ่อน: "ถูกต้อง เป็นข้อจำกัดที่เรารายงานไว้ [ระบุข้อ] เราไม่ได้อ้างเกินนั้น"
- ห้าม: เดาตัวเลข, พูดว่า "น่าจะดีกว่า" โดยไม่มีผล, อ้างผลที่ยังไม่มี
